# Attachment Encryption — full lifecycle design

**Status:** Design (not implementation)
**Date:** 2026-09-20
**Author:** Isolated worktree agent, resolving `skein-6aee` + `skein-larv` + `skein-pnc6`
(the three `blocks: skein-wa1l` gap beads, per `skein-wa1l`'s own reconciliation list).
**Scope:** The full attachment encryption lifecycle — key hierarchy, initial-wrap
authentication, biometric-invalidation recovery, and the test coverage that proves
both hold under interruption. This document is deliberately self-contained: a reader
who has not seen `skein-wa1l` should be able to implement against it.

**Non-negotiables carried forward** (do not weaken; see §6 for the explicit assertion):
- No `INTERNET` permission, no telemetry — irrelevant to this doc's content but binding
  on any implementation (`docs/Handoffs/skein-v1-autonomous-completion.md` §3.1–3.3).
- StrongBox-backed keys, biometric-gated (`docs/Handoffs/skein-v1-autonomous-completion.md`
  §3.15; spec §9 "StrongBox-backed keys, biometric-gated, idle-unload after N minutes").
- All vault data app-private, exposed only via `DocumentsProvider` (§3.15).
- "Fresh design must be reviewed by an actual crypto reviewer before implementation"
  (`skein-wa1l` description, "Non-negotiables"). Nothing here substitutes for that review.

## §1 — Locked decisions (recap from `skein-wa1l`)

### 1.1 What's already locked

`docs/design/POST_REVIEW_RESOLUTIONS.md` lines 13–14 record the locked prior decision
this document must honor without contradiction:

> `skein-wa1l` — enforced immutable-write per attachment UUID; deterministic
> IV = `attachment_uuid[:12]`; retries create a new UUID.

The `skein-wa1l` bead's own DECISION note (2026-09-19) is more specific:

> DECISION 2026-09-19: option 1 — enforced immutable-write per attachment UUID. An
> attachment UUID identifies exactly one plaintext, ever. Retries after crash/interruption
> create a NEW UUID and delete the incomplete prior. Implementation must enforce this at
> the write layer (`WriteOnceAttachmentStore`) and assert (key, iv) uniqueness at runtime.
> This eliminates GCM IV reuse risk by construction, without complex per-write subkey
> derivation. Fresh key per attachment; deterministic IV = `attachment_uuid[:12]` is safe
> under enforced immutability.

Spec (`docs/superpowers/specs/2026-09-19-skein-design.md`) grounds this in the data model:

- §5, line 114: `attachments are referenced by rows in documents with kind='attachment'`,
  stored at `attachments/<uuidv7>`. Attachment content lives as opaque encrypted blobs
  on the filesystem, not inside `vault.db`.
- §5, line 213: `Encryption key wrapping: SQLCipher passphrase derived from a
  StrongBox-backed hardware key, biometric-gated, kept in memory only while unlocked.`
  This is the **vault-open** key hierarchy (SQLCipher passphrase). It is a *different*
  key hierarchy from the one this document defines for attachment content — see §1.3.
  Conflating the two was part of what produced the original GCM-reuse defect.

### 1.2 Why immutable-write is what makes a deterministic nonce safe

AES-256-GCM requires that a given `(key, nonce)` pair is used to encrypt **at most one**
plaintext, ever, under that key. Reusing a nonce under the same key breaks both
confidentiality and authenticity (this is well documented on
`developer.android.com/reference/javax/crypto/Cipher` under the GCM section, and is the
citation the original `skein-wa1l` review pointed at).

Under option 1:

- Each attachment UUID gets a **fresh, unique per-attachment content key**
  (`content_key`, AES-256, generated by `SecureRandom`, never reused across UUIDs).
- The nonce for that content encryption is deterministic: `iv = uuid_bytes[0:12]`
  (the first 12 bytes of the 128-bit UUIDv7, which is already required to be globally
  unique per non-negotiable §3.14, "Every document has a stable UUIDv7").
- Because `content_key` is unique per UUID **and** a UUID identifies exactly one
  plaintext for its entire lifetime (write-once, retries mint a new UUID), the pair
  `(content_key, iv)` is used exactly once, ever, for exactly one plaintext. There is no
  way to reach the GCM-unsafe state "same key, same nonce, different plaintext" without
  also violating the write-once invariant — which the store must enforce (§2, §5).

This is *not* the same guarantee for any key that is reused across many attachments.
That distinction drives §1.3.

### 1.3 The key hierarchy this document adds

Three layers, deliberately kept separate so that "rewrap" (§3) never has to touch
per-attachment ciphertext, and so a fresh biometric prompt can be required per
attachment operation without re-deriving the whole vault's crypto state:

```
Layer 0 (Keystore, non-extractable, per-use auth, StrongBox-backed):
    vault.attachmentWrap.biometric   — AES-256, AUTH_BIOMETRIC_STRONG, 0s validity
    vault.attachmentWrap.credential  — AES-256, AUTH_DEVICE_CREDENTIAL, 0s validity
        Two INDEPENDENT Keystore entries wrapping the SAME Layer-1 secret.
        See §3.2 for why two entries instead of one combined-bitmask entry.

Layer 1 ("attachment master key material" — the thing skein-larv is about):
    master_key_material — 256-bit AES key, software-generated via SecureRandom
    ONCE at vault setup. Persisted ONLY as two wrapped copies (one per Layer-0
    entry) in the `attachment_master_key` table (§3.4). Never cached in process
    memory beyond the scope of a single wrap/unwrap operation (§1.4). Never
    regenerated for the lifetime of the vault except by an explicit, destructive,
    user-initiated "reset vault" (out of scope for this doc).

Layer 2 (per-attachment content key — the "per-use attachment key"):
    content_key — 256-bit AES key, software-generated via SecureRandom, fresh
    for every attachment UUID. Used exactly once: encrypt one plaintext with
    iv = uuid[:12] (§1.2). Immediately wrapped under the transiently-unwrapped
    Layer-1 master_key_material with a RANDOM 96-bit nonce (Layer 1 is reused
    across every attachment, so its wrap nonces cannot be deterministic — see
    §1.5). The wrapped bytes are what's persisted in `attachment_keys` (§2.4).
```

This is a standard envelope-encryption structure with one addition specific to Skein's
threat model: Layer 0 is configured for **per-use** authentication (0-second validity
window), so every single wrap or unwrap of `master_key_material` demands a fresh
`BiometricPrompt`/device-credential challenge — not just "the vault happens to be
unlocked." That is what `skein-6aee`'s title ("per-use attachment keys") and the task's
required `KeyGenParameterSpec` snippet are pointing at: the *Keystore-resident wrapping
key* is per-use-auth, not each of the (many, ephemeral) per-attachment content keys.
Making every one of thousands of small content keys its own Keystore entry would be
impractical and is not what "per-use attachment keys" means here; §1.3 makes that
terminology unambiguous for implementers.

### 1.4 Master key material is never cached across operations

`master_key_material` is unwrapped (Layer 0 → plaintext bytes in memory) **only for the
duration of a single attachment write or read**, then zeroed. It is not cached for the
life of an unlocked session. Concretely:

1. `BiometricPrompt` authorizes a Keystore `Cipher.UNWRAP_MODE`/decrypt operation on
   `vault.attachmentWrap.biometric` (or `.credential` as fallback), recovering
   `master_key_material` as a `ByteArray` in memory.
2. That `ByteArray` is used for exactly one software AES-GCM wrap (write) or unwrap
   (read) of the relevant `content_key`.
3. Both `master_key_material` and (for writes) `content_key` are explicitly zeroed
   (`java.util.Arrays.fill(bytes, 0)`) as soon as step 2 completes, in a `finally` block.

This is deliberately *more* auth friction than a session-cached key would give, not
less — it satisfies "no auth requirement weakened" by construction (§6) and is what
makes §3's rewrap coherent: because `master_key_material` only ever exists transiently
and is always reconstructable from its wrapped form plus a live auth factor, "rewrap"
is a well-defined operation (unwrap old, wrap new, discard old alias) rather than an
ill-defined one over an already-non-extractable hardware key.

### 1.5 Nonce construction, summarized

| What's encrypted | Key | Nonce | Why safe |
|---|---|---|---|
| Attachment plaintext | `content_key` (fresh per UUID) | `uuid[:12]` (deterministic) | `(key, nonce)` used exactly once ever — write-once invariant (§1.2) |
| `content_key` itself (the "wrap") | `master_key_material` (long-lived, reused across every attachment) | random 96-bit, `SecureRandom` per wrap | Key is reused across many attachments, so nonce must be independently random each time; stored alongside ciphertext in `attachment_keys.wrap_iv` |
| `master_key_material` itself | `vault.attachmentWrap.{biometric,credential}` (Keystore, non-extractable) | random 96-bit, `SecureRandom` per (re)wrap | Same reasoning; stored in `attachment_master_key.wrap_iv_*` |

A runtime assertion — `assert(seen.add(Pair(keyId, nonce)))` in a debug/test build,
throwing in an instrumented test harness — is added at each of the three encrypt call
sites per the `skein-wa1l` DECISION note's "assert (key, iv) uniqueness at runtime"
instruction. See §4 for the corresponding test.

## §2 — Initial-wrap authentication flow (resolves `skein-6aee`)

### 2.1 The gap this closes

`skein-6aee`: unwrap-time auth (reading an existing attachment) was assumed covered
elsewhere, but nothing specified whether/how the user authenticates before the *first*
wrap of a brand-new attachment key, and how a cancelled/failed auth interacts with the
write-once invariant. This section is that specification.

### 2.2 When this fires

Every time the app is about to write a **new** attachment: importing a file, saving a
generated export, attaching a chat asset — anything that calls
`WriteOnceAttachmentStore.write(...)` with a UUID that has never been used before.
Per the immutable-write invariant, this is the *only* time a wrap for that UUID ever
happens; there is no "update" path.

### 2.3 Which operation triggers the user-facing prompt

Not the content encryption itself (that's a pure software AES-GCM call using an
in-memory `content_key` — no Keystore involvement, no prompt). The prompt is triggered
by the **unwrap of `master_key_material`**, which is a live Keystore operation against
a per-use-auth key:

```kotlin
KeyGenParameterSpec.Builder("vault.attachmentWrap.biometric", PURPOSE_ENCRYPT or PURPOSE_DECRYPT)
    .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
    .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
    .setIsStrongBoxBacked(true)
    .setUserAuthenticationRequired(true)
    .setUserAuthenticationParameters(0, KeyProperties.AUTH_BIOMETRIC_STRONG)
    .build()
```

(The `.credential` sibling entry uses `KeyProperties.AUTH_DEVICE_CREDENTIAL` in place of
`AUTH_BIOMETRIC_STRONG` — see §3.2 for why these are two entries, not one bitmask-OR'd
entry.) `setUserAuthenticationParameters(0, ...)` means **zero-second validity**: the
key is usable only during the single authenticated `CryptoObject` operation it was
authorized for. Every attachment write (and every read) demands its own fresh prompt.
This is intentional defense-in-depth for high-value attachment content, distinct from —
and in addition to — the vault-level unlock (SQLCipher passphrase, spec §5 line 213).

### 2.4 The flow

```
1.  User action → new attachment write requested with plaintext stream P.
2.  Reserve a UUIDv7 (call it U). Do NOT insert any row referencing U into
    `documents` yet, and do NOT write ciphertext to its final path yet.
3.  content_key = SecureRandom(32 bytes)                      [in-memory only]
4.  Stream-encrypt P with AES-256-GCM(content_key, iv=U[:12])
    → write ciphertext to a TEMP path: attachments/.pending/U.tmp
    (not attachments/U — see §2.5 for why the visible path is reserved
    until full commit).
5.  Build Cipher for UNWRAP_MODE against vault.attachmentWrap.biometric,
    seeded with the CURRENT active attachment_master_key row's
    wrap_iv_biometric / wrap_tag_biometric (§3.4).
6.  Present BiometricPrompt.authenticate(promptInfo, CryptoObject(cipher)).
        Cancel / fail / lockout → go to §2.6 (abort path). U is never observed.
        Success → callback hands back an authorized Cipher.
7.  master_key_material = cipher.doFinal(wrapped_bytes_biometric)   [transient]
8.  wrap_iv2 = SecureRandom(12 bytes)
    wrappedContentKey = AES-256-GCM.encrypt(master_key_material, wrap_iv2, content_key)
9.  Zero master_key_material and content_key (finally block).
10. SINGLE SQLite transaction on vault.db:
        INSERT INTO documents(id=U, kind='attachment', ...)
        INSERT INTO attachment_keys(attachment_uuid=U, wrapped_content_key,
                                     wrap_iv=wrap_iv2, wrap_tag, master_key_version)
    COMMIT.
11. fsync + atomic rename: attachments/.pending/U.tmp → attachments/U.
12. U is now visible to list()/read() callers. Write reported success.
```

### 2.5 Two-phase commit: why "temp path + atomic rename", not "reserved-row"

Two shapes were considered, per the task's own framing:

**Considered: reserved-row.** Insert a `documents` row for `U` immediately at step 2
with a `status='pending'` column; readers filter on `status='visible'`; a background
sweep deletes `status='pending'` rows older than a timeout. Rejected as primary design:
it requires every reader of `documents` (there are several — RAG ingest queueing,
`DocumentsProvider`, the tab list) to remember the filter, and a missed filter is a
silent-observability bug (a `pending` row leaking into a `SELECT * FROM documents`
somewhere becomes an attachment that's listed but unreadable). A write-layer invariant
should not depend on every reader cooperating.

**Chosen: temp-path + deferred DB insert.** Nothing referencing `U` exists in `vault.db`
until step 10's transaction commits, and no file exists at the *final* path `attachments/U`
until step 11's rename commits. Readers need no special-casing: `documents` simply
doesn't have the row, and `attachments/` simply doesn't have the file, until the write
is fully done. This makes "no UUID half-committed" a structural property, not a
convention every call site has to honor. Ordering matters: **the DB transaction commits
before the file rename**, not after — see §4a for why (interruption between the two
must never leave a `documents` row pointing at a missing/still-temp file; the reverse —
a renamed file with no DB row — is safe, because a startup sweep (§2.7) can garbage
collect an orphan file, but a DB row with no file is a read-time crash, not a sweep-able
state).

Rejecting the reserved-row approach for the primary path doesn't forbid a `.pending`
directory sweep as a secondary safety net (§2.7) — the two ideas are complementary,
not exclusive; the DB row is simply never used as the "is this visible" signal.

### 2.6 Abort path (cancel, fail, lockout)

If step 6's `BiometricPrompt` reports `onAuthenticationError` (includes
`ERROR_LOCKOUT`, `ERROR_NEGATIVE_BUTTON`/user cancel, `ERROR_USER_CANCELED`) or
`onAuthenticationFailed` exhausts retry attempts:

1. Delete `attachments/.pending/U.tmp` if it exists.
2. Zero `content_key` if still resident (it was generated at step 3, before the prompt).
3. Do **not** touch `vault.db` — no transaction was ever opened for `U`, so there is
   nothing to roll back.
4. Discard `U`. Report the write as failed to the caller with a typed error
   (`AttachmentWriteError.AuthenticationAborted`, §5.1).
5. **Retry uses a fresh UUID**, never `U` again — this is required by the write-once
   invariant even though `U` was never observably written anywhere; reusing it would
   require re-verifying that absolutely nothing (not even a crashed-mid-sweep temp file)
   references it, which is strictly more fragile than "UUIDs are cheap, mint a new one."

### 2.7 Startup sweep (defense in depth, not the primary invariant)

On every vault unlock, before accepting new writes: scan `attachments/.pending/` and
delete any file older than a short grace window (covers "app process killed between
step 4 and step 6/10/11" — see §4a). Separately, scan `attachments/` for files whose
UUID has no matching `documents` row (covers "killed between step 11's rename and
returning success to the caller" — the DB transaction already committed in that case
per the §2.5 ordering, so this should be unreachable in practice, but the sweep is cheap
insurance against a filesystem-level partial rename on an unusual filesystem). Never
the other direction: a `documents` row with kind='attachment' and no backing file is
NOT swept automatically — it's a data-loss condition that should surface as a visible
read error (§5.1), not be silently deleted, since deleting the row would destroy the
only record that data used to exist.

## §3 — Biometric-invalidation recovery (resolves `skein-larv`)

### 3.1 The gap this closes

`skein-larv`: when Android invalidates a biometric-bound key (new fingerprint enrolled,
biometric data reset), the design must **rewrap the existing `master_key_material`**
under a freshly authenticated key — never generate a replacement master, which would
permanently strand every attachment encrypted before the invalidation.

### 3.2 Two independent Keystore entries, not one combined-bitmask entry

`KeyGenParameterSpec.Builder.setUserAuthenticationParameters` accepts a bitmask that
can combine `AUTH_BIOMETRIC_STRONG` and `AUTH_DEVICE_CREDENTIAL` on a single key entry.
That was considered and **rejected** for the recovery-critical wrapping of
`master_key_material`, for one reason: whether a single combined-factor key entry is
invalidated by a biometric-enrollment change when device-credential is *also* an
allowed factor on that same entry is not something this document asserts confidently —
Android's documented invalidation semantics for `KeyPermanentlyInvalidatedException`
are precise for the single-factor case (`developer.android.com` — biometric enrollment
change invalidates keys requiring `setUserAuthenticationRequired(true)` bound to
biometric) but the interaction with an OR'd device-credential factor on the *same* key
is exactly the kind of platform/vendor-version-dependent detail the `skein-wa1l`
non-negotiable ("fresh design must be reviewed by an actual crypto reviewer") is meant
to catch before it becomes a production surprise.

Using **two separate Keystore entries** — `vault.attachmentWrap.biometric`
(`AUTH_BIOMETRIC_STRONG` only) and `vault.attachmentWrap.credential`
(`AUTH_DEVICE_CREDENTIAL` only) — sidesteps the ambiguity entirely: each entry's
invalidation is scoped only to changes in its own authenticator class. Both
independently wrap identical copies of the same `master_key_material` (§3.4). This is,
if anything, *more* conservative than the combined-entry approach, which is consistent
with "no auth requirement weakened" (§6). If a future crypto review determines the
combined-entry semantics are safe and well-documented for our minSdk, collapsing to one
entry is a valid follow-up — but it is not the default this document specifies.

**Trade-off, stated plainly:** this means the device-credential Keystore entry exists
and is live from day one (not created lazily at first-recovery), because it must
already hold a valid wrapped copy of `master_key_material` *before* any invalidation
happens — recovery cannot depend on a factor that was never provisioned. The cost is:
(a) one extra Keystore entry and one extra wrapped blob to maintain per master-key
generation, and (b) device credential (PIN/pattern/password) is generally weaker than
biometric, so its wrapped copy is a slightly softer target than the biometric one —
but it is already required by the OS to exist as a precondition for enrolling biometrics
at all, so this doesn't introduce a *new* secret class, only a new use of an
already-mandatory one.

### 3.3 Trigger

`KeyPermanentlyInvalidatedException` surfaces from `Cipher.init()` on either
`vault.attachmentWrap.biometric` or `.credential` (§2.4 step 5, or the read-path
equivalent). Per Android's documented semantics this means the specific Keystore key
entry is now, and forever, unusable — there is no operation that recovers it. Recovery
therefore always means "provision a *new* Keystore entry and rewrap," never "fix the
old entry."

### 3.4 Storage shape

```sql
CREATE TABLE attachment_master_key (
  key_version              INTEGER PRIMARY KEY,
  wrapped_bytes_biometric  BLOB,       -- NULL if this factor's entry is currently dead
  wrap_iv_biometric        BLOB,
  wrap_tag_biometric       BLOB,
  wrapped_bytes_credential BLOB,       -- NULL if this factor's entry is currently dead
  wrap_iv_credential       BLOB,
  wrap_tag_credential      BLOB,
  created_at               INTEGER NOT NULL,
  superseded_at            INTEGER    -- NULL = this is the active generation
);

CREATE TABLE attachment_keys (
  attachment_uuid    TEXT PRIMARY KEY REFERENCES documents(id),
  wrapped_content_key BLOB NOT NULL,
  wrap_iv            BLOB NOT NULL,
  wrap_tag           BLOB NOT NULL,
  master_key_version INTEGER NOT NULL REFERENCES attachment_master_key(key_version),
  created_at         INTEGER NOT NULL
);
```

Both tables live inside `vault.db` (SQLCipher-encrypted under the *separate*
vault-open key hierarchy, spec §5 line 213 — no circular dependency, since that
hierarchy doesn't depend on `master_key_material`). `attachment_keys` rows are
**never rewritten** by a rewrap — `master_key_version` is the only thing that changes
generation, and it's a foreign key, not a copy of key material. This is what makes the
key invariant in §3.6 mechanically true rather than merely a design intention: rewrap
touches exactly one table (`attachment_master_key`), and `attachment_keys` is untouched.

### 3.5 Recovery flow

```
1.  Any Keystore op against vault.attachmentWrap.{biometric,credential} throws
    KeyPermanentlyInvalidatedException.
2.  App transitions to VaultState.RecoveryRequired. This freezes new attachment
    writes/reads (consistent with skein-3xyu: lock cancels in-flight sensitive
    operations) but does NOT lock the whole vault if only the attachment-wrap
    layer is affected — SQLCipher's own key hierarchy is independent (§3.4).
3.  UI presents "Verify to continue" using whichever of the two factors did NOT
    just throw (if biometric entry died, prompt for device credential, and
    vice versa).
4.  User authenticates with the surviving factor →
        cipher.init(UNWRAP_MODE, survivingKeystoreEntry, storedIv/tag)
        master_key_material = cipher.doFinal(wrapped_bytes_<survivingFactor>)
5.  Generate a NEW Keystore entry for the factor that died, with a fresh alias
    (e.g. vault.attachmentWrap.biometric.v{N+1}), same KeyGenParameterSpec as
    §2.3 (StrongBox, per-use auth, 0s validity).
6.  new_iv = SecureRandom(12 bytes)
    new_wrapped_bytes = AES-256-GCM.encrypt(master_key_material, new_iv, newKeystoreEntry)
        (a Keystore WRAP_MODE op against the brand-new entry — itself requires
        one more fresh auth challenge against the JUST-created key, which is
        expected: it has never been authorized before.)
7.  Zero master_key_material immediately after step 6.
8.  INSERT a new attachment_master_key row (key_version = N+1) carrying:
      - the surviving factor's EXISTING wrapped_bytes (copied forward unchanged —
        it was never invalidated, no need to rewrap it against itself)
      - the just-rewrapped factor's new_wrapped_bytes / new_iv / new_tag
    UPDATE the active-version pointer to N+1, in the SAME transaction.
    (Old key_version=N row is left in place with superseded_at set — not
    deleted — until step 9 confirms cleanup is safe; see §3.7 failure modes.)
9.  Only after the transaction in step 8 commits: KeyStore.deleteEntry() the
    OLD dead alias (it was already unusable, this just frees the slot).
10. Transition back to VaultState.Unlocked.
```

Note what does **not** happen anywhere in this flow: nothing touches
`attachment_keys`, nothing touches `attachments/<uuid>` files, and
`master_key_material`'s actual bytes are identical before and after — only its
wrapped *envelope* changed. Every attachment wrapped under `key_version = N` remains
wrapped under a `content_key` that's still recoverable, because `master_key_material`
recovered at step 4 is byte-for-byte the same value that originally wrapped it.

### 3.6 Key invariant

**`master_key_material` never changes value across a biometric invalidation.** Only its
Keystore-side wrapping (Layer 0) changes. Every `attachment_keys.wrapped_content_key`
row, regardless of which `master_key_version` it references, remains decryptable by:
unwrap the master material under *whichever* generation's row is referenced → use it to
unwrap that row's `content_key` → decrypt content. Rewrap events add new
`attachment_master_key` rows; they never require touching or re-encrypting old
`attachment_keys` rows, because those rows reference a `master_key_version`, and
recovering *that* version's master material (via whichever of its two wrapped copies is
still live) is always possible as long as at least one of the two factors on that
generation was never simultaneously invalidated (§3.8, residual risk).

### 3.7 Failure modes, enumerated

| Failure point | State left behind | Recovery on next attempt |
|---|---|---|
| Killed after step 4 (master material recovered, in memory) before step 5 | Nothing persisted; `master_key_material` was only ever in memory, now gone with the process | Restart recovery from step 1; surviving factor still intact, unaffected |
| Killed after step 6 (new Keystore entry created + wrapped) before step 8's transaction commits | New Keystore alias exists but is orphaned (no DB row references it yet); old `attachment_master_key` row (key_version=N) is still active and still has the surviving factor's valid wrapped copy | Old generation N is still fully functional via the surviving factor. Next recovery attempt detects the orphaned alias (naming convention `*.v{N+1}` with no matching DB row), deletes it, and starts a clean rewrap attempt — generating yet another new alias if needed. Vault is never stuck: the surviving factor alone is sufficient to keep operating even without ever completing a rewrap. |
| Killed after step 8's transaction commits, before step 9's `deleteEntry` | Both old and new Keystore entries exist; DB already points at key_version=N+1 | Harmless — step 9 is pure cleanup. Next app start (or next recovery-flow entry) retries the `deleteEntry` for the now-confirmed-dead old alias. Decryption already works via key_version=N+1. |
| User abandons recovery (backs out of the "Verify to continue" screen) | `VaultState.RecoveryRequired` persists; no Keystore or DB mutation occurred beyond step 1's exception | Vault stays locked for attachment operations. This is the explicitly correct "consistent locked state" — see §3.8. No attachment is stranded because none were touched; they simply remain unreadable until the user completes recovery. |
| Both factors invalidated simultaneously (e.g., device fully reset both biometric enrollment and credential in one action) | Neither `vault.attachmentWrap.biometric` nor `.credential` can unwrap `master_key_material` | **No automated recovery path exists.** This is a residual gap — see §3.8. Vault remains locked for attachment content; declared out of scope for v1 automated recovery, flagged `needs-human-review`. |

### 3.8 Residual risk (explicitly not resolved here)

If both Layer-0 factors are invalidated in the same event — a full device reset of both
biometric enrollment and device credential — there is no surviving factor to unwrap
`master_key_material`, and by construction (§1.4, `master_key_material` never persisted
in plaintext, never escrowed elsewhere in v1) recovery is not possible. This is a known,
accepted limitation for v1, consistent with the project's practice of escalating
uncertain trade-offs to a human rather than inventing a weaker workaround (spec's
autonomous-loop guidance: "if in doubt about a decision that would affect §3
non-negotiables, STOP and ask the human" —
`docs/Handoffs/skein-v1-autonomous-completion.md` line 871). A v2 candidate — a
user-generated recovery code (PBKDF2/scrypt-derived third wrapped copy, written down at
setup, BIP39-style) — would close this gap but is deliberately **not** specified here:
it introduces a new secret class (a written-down code) with its own storage/UX/threat
model that deserves its own design pass and its own crypto review, not a paragraph
appended to this document. Flagged in §7 for the coordinator to file as a follow-up
bead if desired.

## §4 — Test coverage (resolves `skein-pnc6`)

All tests below assume a `KeyStoreSimulator` test double (§5.3) that can create fake
Keystore entries, simulate `KeyPermanentlyInvalidatedException` on demand
(`KeyStore.deleteEntry` equivalent), and record every `Cipher.init` call's `(keyAlias,
iv)` pair for the runtime-uniqueness assertion (§1.5).

### 4a. Interruption tests (mid-write kill)

1. **Killed after key generation, before encrypt commit.**
   `content_key` generated (§2.4 step 3), process killed before step 4's ciphertext
   write completes. *Assert:* `list()` after restart does not include the reserved
   UUID. `attachments/.pending/` may contain a partial `.tmp` file; the startup sweep
   (§2.7) removes it. *Assert:* retrying the write uses a **new** UUID —
   `WriteOnceAttachmentStore.write()` never accepts a caller-supplied UUID for retry;
   it always mints its own, so this is enforced by API shape, not by convention.

2. **Killed after encrypt (temp ciphertext fully written), before the step-10 DB
   transaction commits.** *Assert:* `list()` does not include the UUID (no `documents`
   row exists). *Assert:* `attachments/.pending/U.tmp` exists but `attachments/U` does
   not. *Assert:* the startup sweep deletes the orphaned temp file. *Assert:* retry
   mints a fresh UUID (same reasoning as test 1).

3. **Killed after the DB transaction commits, before the step-11 atomic rename.**
   *Assert:* this is the one interruption state that is **not** simply "invisible" —
   the `documents` row now exists but `attachments/U` (final path) does not yet, only
   `attachments/.pending/U.tmp` does. This is exactly why §2.5 requires the rename to
   be attempted eagerly and idempotently on next unlock for any `documents` row of
   `kind='attachment'` whose final file is missing but whose `.pending/<uuid>.tmp`
   exists: complete the rename rather than orphaning a committed row. *Assert:* after
   this recovery-rename, `read(U)` succeeds and returns the original plaintext.
   (This is the one case where "retry" means "finish the commit," not "mint a new
   UUID" — because the DB already irreversibly committed to `U`.)

4. **Killed after the rename commits.** *Assert:* `list()` includes `U`. *Assert:*
   `read(U)` succeeds. *Assert:* no retry/recovery action is triggered — this is the
   fully-committed steady state.

5. **Runtime `(key, iv)` uniqueness assertion never fires in a full successful run of
   tests 1–4 repeated N times with N fresh UUIDs.** *Assert:* the `KeyStoreSimulator`'s
   recorded `(keyAlias, iv)` set has no duplicate entries across the whole test run.

### 4b. Failed-auth tests

6. **User cancels the biometric prompt during initial wrap.** Drive
   `BiometricPrompt.AuthenticationCallback.onAuthenticationError(ERROR_USER_CANCELED)`
   via the test double. *Assert:* `write()` returns
   `AttachmentWriteError.AuthenticationAborted`. *Assert:* no UUID is observable via
   `list()`. *Assert:* no file remains under `attachments/` (the `.pending/*.tmp` file
   is deleted per §2.6 step 1 — verify directly, don't rely on the sweep for this
   immediate case). *Assert:* `attachment_keys` and `documents` have no new rows.

7. **User fails biometric N times → `BiometricPrompt.ERROR_LOCKOUT`.** *Assert:*
   `write()` aborts cleanly with the same `AuthenticationAborted` error (or a more
   specific `Locked` variant, §5.1) — not a crash, not a partially-written file.
   *Assert:* the failure is retriable later (lockout is time-bound on the OS side;
   the store itself imposes no additional lockout state).

8. **Failed auth during unwrap on read (existing, previously-committed attachment).**
   *Assert:* `read(U)` returns a typed error (`AttachmentReadError.AuthenticationAborted`)
   — never an exception that could carry partial plaintext in a stack trace or log.
   *Assert:* no plaintext bytes are written anywhere (no temp file created on the read
   path at all — reads are direct-to-caller streams, never staged to disk).
   *Assert:* the underlying ciphertext file and its `attachment_keys` row are
   untouched — a failed read is a no-op with respect to stored state.

9. **`content_key` and `master_key_material` are zeroed even on the abort path.**
   Use a heap-inspection or wrapper-object test (e.g. a `ZeroingByteArray` test double
   that records whether `.fill(0)` was called before garbage collection) to assert
   both transient key materials are wiped in the `finally` block regardless of which
   step aborted.

### 4c. Biometric-invalidation tests

10. **Simulate `KeyPermanentlyInvalidatedException` via `KeyStoreSimulator`'s
    `invalidate("vault.attachmentWrap.biometric")`, then attempt a write.** *Assert:*
    the app transitions to `VaultState.RecoveryRequired` rather than crashing or
    silently falling back. *Assert:* the pending write is aborted the same way as a
    failed-auth write (test 6) — no half-committed UUID.

11. **Complete recovery via the surviving device-credential factor.** *Assert:* a new
    `attachment_master_key` row is inserted with a fresh `key_version`. *Assert:* the
    new row's `wrapped_bytes_biometric` corresponds to a **new** Keystore alias (not
    the dead one — verify via the simulator that a distinct alias was used).
    *Assert:* `wrapped_bytes_credential` in the new row decrypts (via the simulator)
    to the **same** `master_key_material` bytes as the previous generation's row
    (this is the crux assertion for "rewrap, not replace").

12. **All attachments encrypted pre-invalidation still decrypt post-recovery.** Write
    several attachments under `key_version = N`. Invalidate the biometric factor.
    Recover (test 11) to `key_version = N+1`. *Assert:* `read()` on every
    pre-invalidation UUID succeeds and returns byte-identical plaintext, with no
    re-encryption or re-write of any `attachment_keys` row (assert row `updated_at`/
    absence-of-write-count is unchanged — these rows have no `updated_at` column at
    all by design, §3.4, so this is really "assert no `UPDATE`/`INSERT` was issued
    against `attachment_keys` during recovery," checked via a query-log spy on the
    test double's SQLite connection).

13. **Failed recovery (user backs out) leaves the vault in a consistent locked
    state.** Trigger invalidation, present the recovery UI, simulate the user
    dismissing it without authenticating. *Assert:* `VaultState` remains
    `RecoveryRequired` (not silently reverted to `Unlocked`). *Assert:* no
    `attachment_master_key` row was inserted. *Assert:* every existing attachment
    remains un-readable (returns a typed `RecoveryRequired` read error, not a crash
    and not stale plaintext from some cache) until recovery is later completed.
    *Assert:* restarting the app re-enters `RecoveryRequired` rather than forgetting
    the invalidation and re-attempting the dead Keystore alias.

14. **Interrupted rewrap (crash between new-entry creation and DB commit,
    §3.7 row 2).** *Assert:* on restart, the orphaned new Keystore alias is detected
    (no `attachment_master_key` row references it) and deleted. *Assert:* the vault
    is still fully operational via the surviving factor on the OLD (still-active)
    `key_version`. *Assert:* a subsequent recovery attempt succeeds and produces a
    single new generation (not two, i.e. the cleanup doesn't leave duplicate orphan
    aliases accumulating across repeated interrupted attempts).

15. **Both factors invalidated (residual-risk path, §3.8).** *Assert:* the app
    surfaces a distinct, explicit "recovery not possible" state rather than looping
    or presenting a recovery UI that can never succeed. *Assert:* this state does not
    delete or corrupt any `attachment_keys`/`attachment_master_key` rows — data is
    inaccessible, not destroyed, in case a future factor (or v2 escrow mechanism)
    becomes available.

## §5 — Interfaces (sketches, not full impl)

Sketches only — signatures and error types to pin the design, not implementations.

### 5.1 `WriteOnceAttachmentStore`

```kotlin
sealed class AttachmentWriteError : Exception() {
    object AuthenticationAborted : AttachmentWriteError()      // cancel/fail/lockout
    object RecoveryRequired : AttachmentWriteError()            // master key invalidated, unresolved
    data class Io(val cause: Throwable) : AttachmentWriteError()
}

sealed class AttachmentReadError : Exception() {
    object AuthenticationAborted : AttachmentReadError()
    object RecoveryRequired : AttachmentReadError()
    object NotFound : AttachmentReadError()
    data class CorruptCiphertext(val cause: Throwable) : AttachmentReadError()  // GCM tag mismatch
    data class Io(val cause: Throwable) : AttachmentReadError()
}

/**
 * Enforces: one UUID identifies exactly one plaintext, ever. write() always mints
 * its own UUID; callers cannot supply one, which is what makes "retry uses a fresh
 * UUID" a structural guarantee rather than a caller discipline.
 */
interface WriteOnceAttachmentStore {
    /** Returns the newly minted UUID on success. Never overwrites an existing UUID. */
    suspend fun write(plaintext: InputStream, auth: AuthorizationToken): Result<AttachmentUuid, AttachmentWriteError>

    suspend fun read(uuid: AttachmentUuid, auth: AuthorizationToken): Result<InputStream, AttachmentReadError>

    /** Lists only fully-committed attachments — see §2.5 (no reader-side filtering needed). */
    suspend fun list(): List<AttachmentUuid>
}

/**
 * Opaque marker that a BiometricPrompt/device-credential challenge already ran for
 * THIS specific operation. The store's write()/read() still perform their own
 * Keystore Cipher.init() per §1.4 — this token exists so the calling UI layer and
 * the store agree on "one prompt maps to exactly one attempted operation," not so
 * the store can skip authentication.
 */
class AuthorizationToken internal constructor(internal val cryptoObject: BiometricPrompt.CryptoObject)
```

### 5.2 `MasterKeyRecovery`

```kotlin
sealed class RecoveryFactor {
    data class Biometric(val cryptoObject: BiometricPrompt.CryptoObject) : RecoveryFactor()
    data class DeviceCredential(val cryptoObject: BiometricPrompt.CryptoObject) : RecoveryFactor()
}

sealed class RewrapResult {
    data class Rewrapped(val newKeyVersion: Int) : RewrapResult()
    object NoSurvivingFactor : RewrapResult()          // §3.8 residual risk path
    object UserAbandoned : RewrapResult()               // §3.7 row 4 / test 13
    data class Failed(val cause: Throwable) : RewrapResult()
}

/**
 * Never generates new master_key_material. Only ever unwraps an existing generation
 * via a surviving factor and re-wraps the SAME bytes under a fresh Keystore entry
 * for the dead factor. See §3.5–§3.6.
 */
interface MasterKeyRecovery {
    suspend fun attemptRewrap(
        deadFactor: KeystoreAlias,
        survivingFactor: RecoveryFactor,
    ): RewrapResult

    /** True iff `attachment_master_key` has an active row with at least one live factor. */
    suspend fun isRecoveryRequired(): Boolean
}
```

### 5.3 Test helpers — `KeyStoreSimulator`

```kotlin
/**
 * Fake Keystore for instrumented tests. Backs entries with in-memory AES keys
 * (never real hardware) so tests can force invalidation and inspect every
 * Cipher.init() call without a real device's biometric hardware.
 */
interface KeyStoreSimulator {
    fun createEntry(alias: KeystoreAlias, authType: AuthType, strongBoxRequested: Boolean)

    /** Marks `alias` dead: any subsequent Cipher.init() against it throws
     *  KeyPermanentlyInvalidatedException, matching real Keystore behavior after
     *  KeyStore.deleteEntry-equivalent invalidation. */
    fun invalidate(alias: KeystoreAlias)

    fun deleteEntry(alias: KeystoreAlias)

    /** Every (alias, iv) pair passed to Cipher.init() across the simulator's
     *  lifetime, for the §1.5 runtime-uniqueness assertion in tests. */
    fun recordedIvsByAlias(): Map<KeystoreAlias, List<ByteArray>>
}

/** Drives BiometricPrompt callbacks deterministically in tests — success, each
 *  onAuthenticationError code, and onAuthenticationFailed retry exhaustion. */
interface FakeBiometricPrompt {
    fun simulateSuccess(cryptoObject: BiometricPrompt.CryptoObject)
    fun simulateError(code: Int)   // e.g. BiometricPrompt.ERROR_LOCKOUT, ERROR_USER_CANCELED
    fun simulateFailedThenExhausted()
}
```

## §6 — Non-negotiables preserved

Explicit assertions, one per requirement in the task brief:

- **No auth requirement weakened.** Every attachment write and read requires a fresh,
  per-use `BiometricPrompt`/device-credential challenge (0-second Keystore validity,
  §1.4, §2.3) — strictly more friction than the vault-level session unlock alone. The
  two-Keystore-entry design in §3.2 was chosen specifically because it is the more
  conservative option under platform-semantics uncertainty, not the more convenient one.
- **StrongBox-backed keys where available.** Both `vault.attachmentWrap.biometric` and
  `.credential` (and every regenerated successor alias created during recovery, §3.5
  step 5) are created with `.setIsStrongBoxBacked(true)`, matching spec §5 line 213 and
  `docs/Handoffs/skein-v1-autonomous-completion.md` §3.15.
- **Master key material never on disk in plaintext.** `master_key_material` exists only
  as: (a) two independently-wrapped ciphertext blobs in `attachment_master_key`
  (§3.4), or (b) a transient in-memory `ByteArray`, zeroed immediately after each single
  wrap/unwrap use (§1.4). It is never serialized, logged, or written to any file or
  database column in unwrapped form.
- **Immutable-write invariant holds across every failure mode.** §4a enumerates every
  interruption point in the write path and shows the invariant survives each (retry
  mints a fresh UUID in all cases except the single case where the DB already
  irreversibly committed, in which case the correct action is completing the commit,
  not creating a duplicate). §4b and §4c show the same holds under failed-auth and
  biometric-invalidation, respectively — no failure mode described anywhere in this
  document allows the same `(content_key, iv)` pair to encrypt two different plaintexts.
